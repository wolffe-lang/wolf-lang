Title: tests hard-code taskset -c 0-3 / absolute /usr/bin/taskset: a shared host cannot pin them

On a shared Linux host with a lane assigned CPUs 6-11, the inherited
`taskset -c 6-11 cargo ...` affinity does not constrain descendants that
explicitly call `taskset -c 0-3` or `taskset -c 0`. Those commands expand
their affinity into another lane's reserved CPUs. Rootless podman's cpuset
controller is not delegated on hasu, so an outer container does not fix it.

Examples in wolf-lang (s263 based on trunk 7b7b1753):
- crates/wolf_driver/tests/ctrl_c_lanes.rs:316 uses absolute /usr/bin/taskset.
- crates/wolf_driver/tests/atomic_witness.rs:106,115 uses 0-3 and 0.
- crates/wolf_driver/tests/kill_park_lanes.rs:169 uses 0-3.
- crates/wolf_driver/tests/process_calls_lanes.rs:816 uses 0-3.
- crates/wolf_driver/tests/fs_gaps_lanes.rs:640 uses 0-3.
- crates/wolf_driver/tests/exec_lanes.rs:229 has the same four-CPU lane.
Other matches include reactor_lanes, job_wait_lanes, stdfd_lanes,
root_arena_threads_lanes, ids_lanes, group_lanes and signal_gaps_lanes.

Proposal: one shared affinity helper that reads WOLF_TEST_CPUS and chooses
one-/four-CPU subsets of that allocation, or defaults to the current process's
affinity when unset. Do not assume CPU numbering starts at zero. Invoke the
configured taskset from PATH, not an absolute path. Record actual CPU lists
in test labels and fail explicitly when a requested budget cannot fit.

Temporary s263 evidence uses a container-only shim, authorized by R-s263-7,
that maps CPU sets to equal-sized subsets of 6-11 and logs the translations.
No host configuration or existing test files were changed for that shim.
