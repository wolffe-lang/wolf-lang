## Sessions and pseudo-terminals

A program can now start a child in a session of its own and give it a
terminal, which is what a remote login or a terminal multiplexer needs.

`os_spawn_session(exe, args, map, defaults)` starts a child that leads a
new session (`[os.proc.session]` in [the OS chapter](../../spec/11-os.md)):
its session, group and process ids are one number, it has no controlling
terminal, and no key, hangup or background stop of the parent's terminal
reaches it. The descriptor map and `defaults` are placed as
`os_spawn_job` places them. `os_setsid()` moves the calling process into
a session of its own and `os_sid()` reads its session id
(`[os.term.session]`); `os_setsid` is `denied` for a process that leads a
group, and nothing moves.

`os_term_open_pty()` opens a pseudo-terminal and answers its master and
a slave as two close-on-exec handles, neither of them the caller's
controlling terminal (`[os.term.pty]`). `os_term_pty_name(fd)` answers
the slave's name for a master: `/dev/pts/N` on Linux and PAX,
`/dev/ttysN` on macOS. `os_term_set_size(fd, rows, columns, xpixels,
ypixels)` sets all four fields of a terminal's size, and the host signals
`RESIZE` to the foreground group when any of them changes
(`[os.term.size.set]`). `os_term_attr(fd, op)` and `os_term_set_attr(fd,
op, value)` read and set one setting by its RFC 4254 opcode, with RFC
8160's 42: the special characters, the flags, the character size and the
two speeds (`[os.term.attr]`). An opcode the host's terminal driver lacks
(11, 15 and 17 on Linux; 15, 16, 37, 52 and 71 on macOS) is
`unsupported`, and so is a setting the host did not keep, with every
other field as it was.

The order a program follows: open the pair, set the size and the
settings, fork; the child calls `os_setsid` and opens the slave by name,
which makes it the child's controlling terminal; the parent closes its
slave. The runtime's opens pass no `O_NOCTTY`, so a session leader with
no controlling terminal that opens a terminal no session holds takes it,
on Linux and on macOS. Windows answers `unsupported` for all eight
calls. The checked machine performs the five pseudo-terminal calls in the
`wolf` process; comptime refuses them, and the freestanding target
refuses them by name.

## Patterns, names and types the checker now refuses

These were silent or disagreed between tiers in 0.2.38. Each is now a
diagnostic at the offending name, on the checked machine, native and
release alike, and the specification states the rule:

- A literal pattern its scrutinee's type cannot hold is **E0415**:
  `match v { 300 => … }` over a `u8` used to match 44 natively and never
  on the checked machine (`[gram.pat.lit]`,
  [issue 1058](https://github.com/wolffe-lang/wolf-lang/issues/1058)). A
  signed literal pattern is refused by name (E0207) with the guard
  spelling as its fix, and a `u64` literal pattern above `i64::MAX` now
  matches on every machine.
- A name a `match` arm, a `for` header, an `else |…|` handler or a
  `select` receive binds is bound as `let` binds it: assigning it is
  **E0410**, and the fix is `var x = x` at the start of the body
  (`[gram.pat.let]`). The same holds for a bare arm name that tests a
  case (`[gram.pat.nullary.scope]`).
- A name bound twice in one pattern, or a parameter declared twice, is
  the new **E0827** (`[gram.pat.names]`); an or-pattern whose
  alternatives bind different names is the new **E0828**, and one name
  bound at two types is E0401 (`[gram.pat.or]`).
- A variant or a field declared twice is **E0302**
  (`[gram.item.type.names]`); a type that contains itself by value is
  **E0404**, with the cycle named (`[type.rec]`); recursion goes through
  `List`, `Map`, `Pool` or a `handle`, as before.
- An error-set alias is checked where it is declared, used or not
  (E0610 for a loop, E0601 for a tag spelled twice), and an alias's tags
  merge with a row's own in any order (`[type.err.alias.union]`).

## Diagnostics that no longer blame the compiler

A capitalized name that nothing declares is **E0301** at the name where
no error row takes it, with the fixes its position allows
(`[gram.expr.tagident]`,
[issue 1085](https://github.com/wolffe-lang/wolf-lang/issues/1085)); a
tag the function spells where it cannot fail is E0604. A module of the
package that the file does not import says so and offers the `use`. No
prelude name answers "a std/prelude stub without a signature" any more:
each answers by its class.

`min(a, b)` compiles on every tier: two values of one integer type, the
smaller as that type, each operand evaluated once. The free `zip` says
that `xs.zip(ys)` is the spelling. `wolf build` names the `ld.lld` it
links with on Linux, and `WOLF_LD=cc` (or `--linker cc`) links with the
system linker instead. `wolf add` and `wolf init` quote every manifest
string so that the manifest they write reads back.

## A program started with standard output closed

On Linux with glibc, a program given 8 or more CPUs and started with
descriptor 1 closed could, for a few microseconds while its first worker
threads started, see a descriptor of the C library's on 1: glibc reads
the CPU count once a program runs more threads than its arena bound,
and the read took the lowest free descriptor. The runtime now settles
glibc's arena limit before `main` and raises it when the pool first
starts, from main and before the first worker: no other thread reads
the CPU count while the program runs
([issue 1051](https://github.com/wolffe-lang/wolf-lang/issues/1051)).
The race test that failed intermittently on such hosts at 0.2.37 and
0.2.38 has a row of its own now, which traces the reads.
`MALLOC_ARENA_MAX`, or an arena limit in `GLIBC_TUNABLES`, is left as the
user set it. One program allocates differently: one whose C library
starts more than 8 threads before the program starts its first task;
those threads share 8 arenas until the pool starts.

## Paired interpreter

Lupin 0.1.61 resolves the eight new names. It answers every row a call
decides before it reaches a session or a terminal (the shapes, the
windows rows, the opcodes a host lacks, a forged or closed handle), and
every call that would reach a session or a terminal is refused by name:
Rust's standard library has no stable way to make either, and lupin
admits no `unsafe`. So `corpus/os/pty_rows.lu` runs to its declared
output on lupin, and `corpus/os/session_rows.lu` is `unsupported` there,
refused at the spawn by name.

Lupin gives the compiler's code at the compiler's span for the
front-end rulings (E0410, E0302, E0827, E0828, E0404, E0601, E0609), for
the undeclared name (E0301, E0604) and for a signed literal pattern
(E0207). A literal pattern outside its type traps `overflow` at the
literal when the arm is tested, lupin's dynamic counterpart of E0415.
Lupin does not mirror `min`'s clause or the prelude stubs' classes:
it still runs `min` over any number of integers.

Lupin's spec and corpus pin is wolf-lang `5f1f1c94`, which predates the
corpus rows of 0.2.38 and of this release; they reach lupin's vendored
corpus at its next pin advance.

## Standard library

The bundled std adds the password hash. `std.x.crypto.scrypt` is scrypt
(RFC 7914) and PBKDF2-HMAC-SHA-256 (RFC 8018), with the peak memory
checked against the caller's cap before anything is allocated.
`std.x.crypto.passwd` reads and writes crypt(5)'s `$7$` string: `hash`
gives the string Ubuntu 24.04's crypt gives for the same password, salt
and cost, and `verify` compares in constant time. ROMix is not
constant-time, by scrypt's design. The fixed tree holds 634 tests.

The std's own interpreter ledgers lag the paired lupin, as they did at
0.2.38; advancing them is tracked in
[wolf-std issue 125](https://github.com/wolffe-lang/wolf-std/issues/125).
One limit of the TLS client is known and not fixed: a TLS `read` reports
a clean close, a fatal alert and a bare end of stream alike
([wolf-std issue 133](https://github.com/wolffe-lang/wolf-std/issues/133)).

## Known limits

- A region taken as a value (`let r = region()`) is never freed on the
  native tier; the block form is
  ([issue 1092](https://github.com/wolffe-lang/wolf-lang/issues/1092)).
- E1010's suggested `copy` does not converge: each added `copy` meets the
  same error ([issue 1093](https://github.com/wolffe-lang/wolf-lang/issues/1093)).
- A rejected `wolf build` whose output is piped into a reader that
  closes early exits 101 instead of 2
  ([issue 1094](https://github.com/wolffe-lang/wolf-lang/issues/1094)).
- A `for` over a struct value is declined with exit 4 and no code, and an
  E0402 in the loop's expression goes unreported
  ([issue 1095](https://github.com/wolffe-lang/wolf-lang/issues/1095)).
- A compiled object embeds the working directory and the source path as
  spelled, so the same source built from two directories differs
  ([issue 1088](https://github.com/wolffe-lang/wolf-lang/issues/1088)).

## Archives

There are four compiler host archives and a fifth companion runtime,
`wolf-rt-0.2.39-x86_64-unknown-linux-musl.tar.gz`. The latter is not a
musl compiler executable; that remains tracked in wolf-lang issue 887.
Take compiler objects and runtime from the same release. Release
publication verifies archive and runtime digests, and archive readback
and the release-tier checks are part of that workflow.
