## One wait over files, sockets and signals

A server that owns pseudo-terminal masters, pipes, a listening socket and
its clients, a timer and signals can now wait in one place and learn of
every handle that is ready, so that no busy handle starves the rest. A
terminal multiplexer and an ssh server both need this.

`os_wait_ready(entries, set, deadline_ms)` waits on fs handles and net
handles together, with a set of signal meanings and a deadline
(`[os.ready.wait]` in [the OS chapter](../../spec/11-os.md)). An entry
is an fs handle (a pty master, a pipe, a terminal, a regular file) or,
with bit 61 set, a net handle (a listener or a stream); bit 62 asks
whether the handle takes a write, as in `os_signal_wait_fds`. The answer
is `([index, facts, …], meaning)`: every entry ready at that moment, in
list order, each with its facts (1 read, 2 write, 4 hangup, 8 error), and
the one meaning taken, or 0. A meaning never hides the entries; both
come in one answer. The deadline is `os_signal_wait_fds`'s: 0 looks once,
-1 never passes. Each call polls a duplicate of every entry, so it costs
the length of the list, and it is the form for a list that changes every
wait.

`os_ready_open()`, `os_ready_set(r, handle, interest, key)`,
`os_ready_wait(r, set, deadline_ms)` and `os_ready_close(r)` are a
readiness set the kernel holds (`[os.ready.set]`): epoll on Linux and on
PAX, which runs the Linux binary, and kqueue on macOS. An entry is added
once, under a key of the caller's, with interest 1 (read), 2 (write) or 3
(both); interest 0 removes it. A wait answers `([key, facts, …],
meaning)` for every ready entry and costs what is ready rather than what
is held. A regular file, a directory and a descriptor the kernel's set
will not hold (`/dev/null`, macOS's `/dev/tty`, PAX's console) are polled
beside the set on every wait. Closing a handle (`fs_close`, `net_close`)
removes it from every set, so no wait answers the key of a closed handle.
A set made before `os_fork` answers `io` in the child. What each host
reports as a ready entry's facts, measured, is the table in
`[os.ready.facts]`.

`net_write_some(fd, bytes)` makes one send and answers how many bytes the
host took (`[os.net.write.some]`). It never parks: `busy` when the socket
can take nothing now, `closed` for a peer that has gone, with no SIGPIPE.
A server keeps an output queue for each client, drops what each send
took, and asks the set for write interest while the queue holds bytes.
`net_peer_cred(fd)` answers the pid, uid and gid of the process at the
other end of a connected Unix-domain stream, as the host recorded them at
the connection (`[os.net.peer.cred]`); on macOS the pid is known only
while the peer is connected, and is -1 after it closes.

The waits and the set are served on Linux and macOS. Windows and FreeBSD
answer `unsupported` by name; `net_wait` still serves a wait on sockets
alone there. `net_peer_cred` is `unsupported` on Windows. The checked
machine serves all seven calls on its own tables, polling its set entry
by entry. Comptime refuses them, and the freestanding target refuses them
by name. A program that names `os_wait_ready` or `os_ready_wait` starts
the signal hub before `main`, as one that names `os_signal_wait_fds`
does. `os_signal_wait_fd`, `os_signal_wait_fds` and `net_wait` answer as
before.

## Paired interpreter

Lupin 0.1.62 resolves the seven new names. It serves `net_write_some`:
one write on the stream, which lupin already holds non-blocking. It
answers every row the compiler decides before the host (a refused
meaning set, a deadline below -1, Windows, a wait nothing could end, a
forged or closed handle, an interest or a key out of range), and every
wait, every set and a Unix stream's credentials are refused by name:
Rust's standard library has no `poll`, `epoll` or `kqueue`, its
`peer_cred` is unstable, and lupin admits no `unsafe`. So
`corpus/os/ready_rows.lu` is `unsupported` on lupin, refused at its first
wait by name, where 0.1.61 answered that the names do not resolve.

Lupin's spec and corpus pin is wolf-lang `5f1f1c94`, which predates the
corpus rows of 0.2.38 and later; they reach lupin's vendored corpus at
its next pin advance.

## Standard library

The bundled std moves to wolf-std `be1d10fa` and adds two surfaces.

Sessions and pseudo-terminals, over 0.2.39's calls: `std.process` gains
`start_session`, a child that leads a new session with no controlling
terminal, `lead_session` and `own_session`; `std.term` gains `Pty`,
`open_pty`, `pty_name`, `set_size`, `attr`, `set_attr` and
`open_controlling`. `Pty`'s documentation gives the order a server
follows to run a login shell on a terminal.

`std.poll` is one waiter over files and sockets: `Waiter`, `open`,
`add_file`, `add_socket`, `add_listener`, `modify`, `remove` and
`wait`, which answers every ready entry with its facts and the meaning
it took. In this std it is built on 0.2.39's narrower waits, so a waiter
holds files with a set of meanings, or sockets with read interest and no
meanings; files and sockets in one waiter, sockets with meanings or write
interest, and files with no meanings answer `unsupported` on every host,
by name. The calls this release adds are the ones that serve those, and
`std.poll` moves onto them in a later std.

The std's lupin ledger rows that lagged at 0.2.39 run on the paired
lupin now. One limit of the TLS client is known and not fixed: a TLS
`read` reports a clean close, a fatal alert and a bare end of stream
alike ([wolf-std issue 133](https://github.com/wolffe-lang/wolf-std/issues/133)).

## Known limits

- On macOS, the std's `term/pty_child` row is red
  ([wolf-std issue 147](https://github.com/wolffe-lang/wolf-std/issues/147)).
  The row starts `/bin/sh` in a new session with a pty slave on its
  standard descriptors and expects it to have no controlling terminal.
  The spawn gives it none, on Linux and on macOS, but bash takes a
  terminal it finds on its standard input as it starts, and macOS's
  `/bin/sh` is bash where Ubuntu's is dash. A program started this way
  that is a shell may therefore be hung up when the master closes. The
  row and the std's documentation are to be fixed in wolf-std.
- The nightly's large property sweep is red on one mutation: a swapped
  return-type token in one nested `match` file draws four cascade
  diagnostics where the sweep allows three
  ([issue 1057](https://github.com/wolffe-lang/wolf-lang/issues/1057)).
  It concerns diagnostics on invalid source only.
- In the release tier, whether a single-use function is inlined depends
  on how codegen packs the program into clusters, so a change in one part
  of a program can inline or keep functions elsewhere, and no attribute
  keeps a function out of line
  ([issue 1104](https://github.com/wolffe-lang/wolf-lang/issues/1104)).
- `wolf build` of a program the size of the editor yew runs out of memory
  on a PAX guest with 2 GiB or 4 GiB
  ([issue 1103](https://github.com/wolffe-lang/wolf-lang/issues/1103)).
- A region taken as a value (`let r = region()`) is never freed on the
  native tier; the block form is
  ([issue 1092](https://github.com/wolffe-lang/wolf-lang/issues/1092)).
- E1010's suggested `copy` does not converge: each added `copy` meets the
  same error ([issue 1093](https://github.com/wolffe-lang/wolf-lang/issues/1093)).
- A rejected `wolf build` whose output is piped into a reader that
  closes early exits 101 instead of 2
  ([issue 1094](https://github.com/wolffe-lang/wolf-lang/issues/1094)).
- A `for` over a struct value is declined with exit 4 and no code, and an
  E0402 in the loop's expression goes unreported
  ([issue 1095](https://github.com/wolffe-lang/wolf-lang/issues/1095)).
- A compiled object embeds the working directory and the source path as
  spelled, so the same source built from two directories differs
  ([issue 1088](https://github.com/wolffe-lang/wolf-lang/issues/1088)).

## Archives

There are four compiler host archives and a fifth companion runtime,
`wolf-rt-0.2.40-x86_64-unknown-linux-musl.tar.gz`. The latter is not a
musl compiler executable; that remains tracked in wolf-lang issue 887.
Take compiler objects and runtime from the same release. Release
publication verifies archive and runtime digests, and archive readback
and the release-tier checks are part of that workflow.
